CyborgDB persists encrypted indexes to local disk or to S3. Both backing stores run on **Appendix**, CyborgDB's storage engine: an append-only, segmented log with an in-memory hash index. Appendix is built for the access pattern encrypted vector search produces, which is point lookups by random, hash-derived keys. Writes are sequential appends, reads are one hash lookup plus one disk read, and space from deletes and updates is reclaimed by background compaction.

CyborgDB encrypts every record before it reaches Appendix, so the backing store only ever holds ciphertext.

<img src="/images/cyborgdb-search-overview.png" alt="CyborgDB RAG Overview" />

<Note>
**Storage surface.** CyborgDB supports `disk` (the default) and `s3` (AWS S3 or any S3-compatible store) in both deployment models.
</Note>

<Warning>
**v0.18 changes the storage format.** Indexes written by v0.17 or earlier can't be opened by v0.18. Pointing v0.18 at an existing data directory or bucket opens an empty database and leaves the old data untouched. An index also can't be moved between the disk and S3 backing stores in either direction. See [What's New in v0.18](./whats-new#upgrading-from-v0-17) for the re-ingest steps.
</Warning>

## Disk

*Available in: Service · Embedded*

**Persistent local storage for single-node deployments**

The disk backing store keeps the Appendix log on the local filesystem, with no network dependency. It is the default and the recommended choice for single-node deployments.

### Key Benefits

**No Network Dependency**
All data is stored locally. No external database server to configure or manage.

**Persistent Storage**
Data survives process restarts.

**Optional In-RAM Caching**
Each store (vectors, metadata, IDs, metadata index) can be served from an in-RAM cache over the durable log, for memory-speed reads without giving up persistence.

**Best For:** Embedded and single-machine deployments, edge devices, and local development.

## Amazon S3

*Available in: Service · Embedded*

**Cloud object storage for cloud-native deployments**

CyborgDB supports AWS S3 and S3-compatible stores (MinIO, Cloudflare R2, single-site Ceph) as a backing store, so you don't have to manage a database server. Reads are served from an in-RAM cache over S3.

### Key Benefits

**Scalable Capacity**
Object storage grows with your data, with no capacity planning.

**Managed Infrastructure**
No database servers to patch, tune, or back up.

**S3-Compatible**
Works with AWS S3, MinIO, Cloudflare R2, and single-site Ceph.

### Requirements

- **One writer per bucket and prefix.** A second concurrent writer to the same bucket and prefix is a fatal error. Give each writer its own prefix.
- **Write credentials.** Opening an S3 store writes its manifest, so read-only credentials can't open it.
- **Strong consistency.** The store needs strong LIST-after-write consistency. AWS S3, MinIO, Cloudflare R2, and single-site Ceph provide it; multi-site Ceph RGW does not and is not supported.
- **Writes are durable on return.** A write returns only after the S3 object that covers it is durable, so write throughput depends on S3 round-trip latency.

**Best For:** Cloud-native deployments and teams already running on S3 or S3-compatible storage.

## Choosing the Right Backing Store

<Tabs>
  <Tab title="Use Disk">
    - **Single-node deployment.** You want persistent local storage with no external dependencies.
    - **Edge devices.** The hardware has no network access to object storage.
    - **Lowest latency.** Local reads, optionally cached in RAM.
    - **Default choice.** It works out of the box.
  </Tab>

  <Tab title="Use S3">
    - **Cloud-native.** Your infrastructure already uses AWS or S3-compatible storage.
    - **Durability without servers.** You want durable storage without running a database.
    - **MinIO / R2.** You want S3-compatible storage on-premises or in a private cloud.
  </Tab>
</Tabs>

<Note>
The `memory` backing store was removed in v0.18. For memory-speed reads, use the disk store with in-RAM caching enabled. For throwaway test indexes, point the disk store at a temporary directory.
</Note>

## Configuration Examples

### Embedded library

```python Disk
from cyborgdb_core import StorageConfig

# Local disk
storage = StorageConfig.disk("/var/lib/cyborgdb")

# Local disk, with every store served from an in-RAM cache
storage = StorageConfig.disk(
    "/var/lib/cyborgdb",
    cache_vectors=True,
    cache_metadata=True,
    cache_ids=True,
    cache_metadata_index=True,
)
```

```python S3
from cyborgdb_core import StorageConfig, S3Credentials

# AWS S3, credentials from the default AWS provider chain
storage = StorageConfig.s3("my-bucket", region="us-east-1", prefix="cyborgdb/")

# MinIO (S3-compatible) with explicit credentials
storage = StorageConfig.s3(
    "my-bucket",
    endpoint="http://localhost:9000",
    credentials=S3Credentials(access_key="minioadmin", secret_key="minioadmin"),
)
```

See [`StorageConfig`](../embedded/python/types#storageconfig) for every option.

### Service

Select via the `CYBORGDB_DB_TYPE` environment variable (or the equivalent YAML key). See [Environment Variables](../service/guides/advanced/env-vars) for the full list.

```bash
# disk (default)
export CYBORGDB_DB_TYPE=disk
export CYBORGDB_DISK_PATH=/var/lib/cyborgdb   # optional

# s3
export CYBORGDB_DB_TYPE=s3
export CYBORGDB_S3_BUCKET=my-bucket
export CYBORGDB_S3_REGION=us-east-1
export CYBORGDB_S3_PREFIX=cyborgdb/           # optional
```
